# Research & Technical Decisions: Проект «Ургент линия» в Jira Software

**Feature**: [spec.md](file:///d:/Anti/specs/003-urgent-line-jira/spec.md) | **Date**: 2026-09-08

---

## 1. Архитектурный выбор: Тип проекта и Kanban-доска

### Решение
Создать проект типа **Jira Software** с ключом **`URG`** («Ургент линия») и основной доской **Kanban Board**, объединенной со схемой отслеживания SLA через Jira Service Management / Automation.

### Обоснование
* Kanban-доска предоставляет ургентологам и руководству сквозную визуализацию («Single Pane of Glass») текущей загрузки, исключая необходимость переключения между десятками вкладок.
* Колонки Kanban-доски жестко сопоставляются со статусами жизненного цикла: `Новый` → `Принят в работу` → `Эскалирован` → `В работе` → `Ожидание информации` → `Решение принято` → `Закрыт`.
* Цветовая дифференциация карточек по JQL (Card Colors) позволяет мгновенно визуально выделять тикеты `P1` (ярко-красный) и `P2` (оранжевый).

### Рассмотренные альтернативы
* *Scrum-проект*: Отклонен, так как инцидентный поток непрерывен и не укладывается в итеративные спринты.
* *Стандартная очередь JSM без доски*: Отклонена, так как скрывает общую динамику распределения задач и не позволяет оперативно оценивать «бутылочные горлышки» смены.

## 2. Схема полей (Custom Fields) и экранные формы (Screens)

### Решение
Реализовать единый специализированный экран инцидента (`URG: Incident Screen`), используемый для операций `Create`, `Edit` и `View`, с разделением на смысловые вкладки (Tabs):
1. **Основное**: Заголовок (`Summary`), Тип инцидента (`customfield_incident_type`), Приоритет (`Priority`), Описание ситуации (`Description`), Вложения (`Attachment`).
2. **Локация и Контекст**: Торговая точка (`customfield_branch`), Город (`customfield_city`), Дата и время происшествия (`customfield_incident_datetime`), Количество пострадавших (`customfield_affected_count`).
3. **Заявитель и Риски**: Контакт клиента (`customfield_client_contact`), Угроза госорганов (`customfield_threat_gov`), Угроза СМИ/соцсети (`customfield_threat_media`), Ссылка на публикацию (`customfield_media_url`).
4. **Резолюция**: Решение / Принятые меры (`customfield_resolution_summary`).

### Справочник значений «Тип инцидента»
* `Отравление / подозрение на отравление`
* `Угроза обращения в государственные органы`
* `Обращение государственных органов`
* `Жалоба блогера`
* `Жалоба СМИ`
* `Угроза публичной огласки`
* `Массовая жалоба`
* `Репутационный риск`
* `Юридический риск`
* `Угроза жизни или здоровью`
* `Другие критические ситуации`

### Обоснование
Группировка полей по вкладкам предотвращает перегрузку интерфейса при создании тикета сотрудником отдела жалоб (время создания ≤ 90 сек) и гарантирует сохранение полного набора криминалистических данных.

## 3. Архитектура рабочего процесса (Workflow) и прямая эскалация P1

### Решение
Настроить кастомный граф Workflow со следующими переходами:
* `Create` → `Новый`
* `Новый` → `Принят в работу` (для P2–P4)
* `Новый` → `Эскалирован` (**Прямая мгновенная эскалация для P1** в 1 клик)
* `Принят в работу` → `Эскалирован` (ручная эскалация при повышении рисков)
* `Эскалирован` → `В работе` (взятие на контроль старшим ургентологом / Incident Commander)
* `Принят в работу` / `В работе` ⇄ `Ожидание информации` (с фиксацией причины паузы)
* `В работе` → `Решение принято` (с экраном обязательного ввода резолюции)
* `Решение принято` → `Закрыт` (верификация решения и закрытие тикета)
* `Решение принято` → `В работе` (возврат на доработку при неудовлетворительном результате)

### Обоснование
Прямой переход `Новый` → `Эскалирован` удовлетворяет требованию Принципа I Конституции (запрет последовательной эскалации L1→L2 для P1) и позволяет немедленно инициировать Swarming Protocol.

## 4. Модель прав доступа: Персональные учетные записи vs Единый аккаунт

### Решение
Утвердить модель с **персональными учетными записями** сотрудников отдела жалоб и ургентологов, объединенными в группу **`Urgent Team`**.
* Доступ к проекту `URG` закрыт в схеме разрешений (`Permission Scheme`) для группы `jira-software-users` и группы `Anyone`.
* Разрешения `Browse Projects`, `Create Issues`, `Edit Issues`, `Assign Issues`, `Transition Issues` делегируются исключительно:
  - Группе `Urgent Team`;
  - Проектной роли `Urgent Managers` (руководство направления);
  - Группе администраторов `jira-administrators`.

### Обоснование
* Использование общего/анонимного аккаунта нарушает Принципы III и IV Конституции проекта, приводит к обезличиванию ответственности и невозможности установить, кто именно изменил статус или комментарий.
* Персональные учетные записи гарантируют 100% достоверность истории Jira и предотвращают несанкционированный доступ к чувствительным материалам инцидентов.

## 5. Механизм автоматических уведомлений и контроля сроков (SLA)

### Решение
1. **Многоканальное оповещение**:
   * Для `P1`: Webhook / Jira Automation отправляет мгновенное уведомление назначенному исполнителю и руководителю через Email + Telegram-интеграцию (время доставки ≤ 60 сек).
   * Для `P2`: Уведомление назначенному исполнителю.
2. **Сторожевой таймер эскалации (Deadlock Watchdog)**:
   * Правило Jira Automation, срабатывающее каждые 2 минуты: если тикет `P1` находится в статусе `Новый` или `Эскалирован` без изменения статуса или комментария более 5 минут, инициируется повторный громкий алерт руководителю (`URGENT ESCALATION TIMEOUT`).
3. **Календари и цели SLA**:
   * `P1 SLA First Response`: 15 минут, календарь 24/7/365.
   * `P1 SLA Resolution`: 2 часа, календарь 24/7/365.
   * `P2 SLA First Response`: 30 минут, расширенный график.
   * `P2 SLA Resolution`: 4 часа, расширенный график.
   * При статусе `Ожидание информации` таймер останавливается (Stop Condition / Pause).
   * При достижении 75% и 90% расхода времени карточка маркируется предупреждающим тегом `#sla-warning-75` / `#sla-warning-90`.

## 6. Конфигурация аналитического Dashboard

### Решение
Создать Dashboard «Ургент линия» с 9 JQL-виджетами:
1. **Активные P1**: `project = URG AND priority = P1 AND statusCategory != Done ORDER BY created ASC`
2. **Активные P2**: `project = URG AND priority = P2 AND statusCategory != Done ORDER BY created ASC`
3. **Все открытые тикеты**: `project = URG AND statusCategory != Done ORDER BY priority ASC, created ASC`
4. **Просроченные инциденты**: `project = URG AND statusCategory != Done AND (labels = "sla-breached" OR "Time to resolution" = breached())`
5. **Счетчик инцидентов**: Two-Dimensional Filter Statistics (`created >= startOfDay()`)
6. **Распределение по типам**: Pie Chart по полю `customfield_incident_type`
7. **Распределение по торговым точкам**: Heatmap / Filter Statistics по полю `customfield_branch`
8. **Время реакции**: Service Desk SLA report / Resolution Time Graph
9. **Время решения**: Created vs Resolved Graph
