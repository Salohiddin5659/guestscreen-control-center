# Implementation Plan: Проект «Ургент линия» в Jira Software

**Branch**: `003-urgent-line-jira` | **Date**: 2026-09-08 | **Spec**: [spec.md](file:///d:/Anti/specs/003-urgent-line-jira/spec.md)

**Input**: Пользовательский план реализации из 14 этапов для развертывания проекта «Ургент линия» в Jira Software с Kanban-доской, специальными полями, шкалой приоритетов P1–P4, рабочим процессом с прямой эскалацией P1, изолированным доступом через группу Urgent Team, контролем SLA и оперативным Dashboard.

---

## Summary

Развертывание и ввод в эксплуатацию изолированного проекта Jira Software «Ургент линия» (ключ `URG`) с визуальным управлением на Kanban-доске, 15 структурированными полями карточки инцидента, кастомным рабочим процессом с прямой эскалацией критических инцидентов P1, жестким контролем соблюдения регламентных сроков (SLA реакции ≤ 15 мин, решения ≤ 2 ч в режиме 24/7), многоканальным оповещением и аналитическим Dashboard из 9 информационных панелей.

---

## Technical Context

* **Платформа / Система**: Atlassian Jira Software (REST API v2, Jira Automation, инстанс `jsm.oqtl.uz`).
* **Тип проекта**: Jira Software Project (`software`) с типом доски `kanban`.
* **Язык / Инструменты автоматизации**: Python 3.12 (Requests, Psycopg2), Jira Automation Engine, Webhooks.
* **Хранилище данных и аудит**: Реляционная СУБД Jira (PostgreSQL) + центральная база мониторинга и аудита (PostgreSQL 16).
* **Среда развертывания**: Выделенный сервер мониторинга и администрирования Jira в корпоративном сетевом контуре.
* **Целевые показатели производительности**:
  - Время создания тикета: ≤ 90 секунд.
  - Скорость выполнения перехода мгновенной эскалации P1: ≤ 5 секунд.
  - Доставка экстренных нотификаций P1: ≤ 60 секунд.
  - Скорость загрузки и обновления Dashboard с 9 виджетами: ≤ 3 секунд.
* **Ключевые ограничения**:
  - Строгий запрет общих/анонимных учетных записей (только персональные аккаунты участников группы `Urgent Team`).
  - Абсолютная изоляция проекта `URG` от пользователей, не входящих в утвержденную рабочую группу.
  - Неизменяемость автора задачи (`Reporter`) и истории переходов (`History`).
* **Масштаб проекта**: До 500 критических инцидентов в месяц, до 50 активных сотрудников с персональным доступом, 100% покрытие торговых точек сети.

## Work Breakdown: 14 этапов реализации

### Этап 1: Создание проекта «Ургент линия»
* Зарегистрировать проект в Jira Software: Имя — `Ургент линия`, Ключ проекта — `URG`.
* Назначить руководителя проекта (Project Lead) и привязать профиль типа `software`.

### Этап 2: Настройка Kanban board
* Создать специализированную Kanban-доску для проекта `URG`.
* Сконфигурировать колонки доски:
  1. `Новые` (статус `Новый`)
  2. `Приняты в работу` (статус `Принят в работу`)
  3. `Эскалированы` (статус `Эскалирован`, визуальное выделение)
  4. `В работе` (статус `В работе`)
  5. `Ожидание` (статус `Ожидание информации`)
  6. `Решение принято` (статус `Решение принято`)
  7. `Закрыты` (статус `Закрыт`)
* Настроить цветовую дифференциацию карточек (Card Colors): `P1` — ярко-красный, `P2` — оранжевый.

### Этап 3: Создание Issue Types
* Создать и зарегистрировать тип задачи: `Ургентный инцидент` (Urgent Incident).
* Сформировать схему типов задач `URG: Issue Type Scheme` и назначить ее единственной для проекта `URG`.

### Этап 4: Создание поля «Тип инцидента» и схемы полей (15 полей)
* Создать кастомное поле `Тип инцидента` (Single Select) с 11 регламентными значениями (отравление, госорганы, блогеры, СМИ, угроза жизни/здоровью и др.).
* Создать и подключить остальные специализированные поля: `Дата и время происшествия`, `Торговая точка`, `Город`, `Контакт клиента`, `Угроза обращения в госорганы`, `Угроза публикации в СМИ/соцсетях`, `Ссылка на публикацию`, `Количество пострадавших`, `Принятые меры / Резолюция`.
* Сконфигурировать экранные формы `URG: Incident Screen` с группировкой по вкладкам.

### Этап 5: Настройка шкалы приоритетов P1–P4
* Создать и привязать схему приоритетов `URG: Priority Scheme`:
  - `P1 — Критический`
  - `P2 — Высокий`
  - `P3 — Средний`
  - `P4 — Низкий`
* Настроить иконки и цветовую палитру приоритетов.

### Этап 6: Настройка Workflow (Рабочего процесса)
* Спроектировать и активировать схему рабочего процесса `URG: Workflow Scheme`.
* Реализовать прямой бесшовный переход из статуса «Новый» в «Эскалирован» для тикетов с приоритетом `P1`.
* Настроить валидаторы:
  - Запрет перехода в «Решение принято» без заполнения поля резолюции.
  - Закрытие тикета разрешено только из статуса «Решение принято» уполномоченными лицами.

### Этап 7: Настройка ролей и прав доступа (Permission Scheme)
* Создать проектную схему разрешений `URG: Permission Scheme`.
* Исключить группу `jira-software-users` и анонимных пользователей из прав `Browse Projects`.
* Запретить удаление задач (`Delete Issues = None`) для сохранения непрерывного аудит-следа.

### Этап 8: Создание и наполнение группы Urgent Team
* Создать системную группу пользователей `Urgent Team`.
* Добавить персональные учетные записи сотрудников отдела жалоб и дежурных ургентологов (отказ от единого общего аккаунта).
* Назначить группу `Urgent Team` в проектную роль исполнителей проекта `URG`.

### Этап 9: Настройка уведомлений и системы оповещений
* Создать схему уведомлений `URG: Notification Scheme`.
* Настроить немедленную отправку уведомлений ответственному и руководителю при появлении `P1`.
* Настроить уведомление ответственному при создании `P2`.
* Подключить внешние оповещения (Email / Webhook / Telegram).

### Этап 10: Настройка SLA и автоматических эскалаций
* Сконфигурировать цели SLA:
  - P1: First Response ≤ 15 мин, Resolution ≤ 2 ч (24/7/365).
  - P2: First Response ≤ 30 мин, Resolution ≤ 4 ч.
* Настроить автоматическую паузу учета времени в статусе «Ожидание информации».
* Активировать сторожевой таймер автоматической эскалации: алерт руководителю при отсутствии реакции на P1 более 5 минут.
* Настроить предупреждающие триггеры при расходе 75% и 90% лимита времени SLA.

### Этап 11: Создание аналитического Dashboard
* Создать общекорпоративную панель «Dashboard: Ургент линия».
* Развернуть и настроить все 9 регламентных блоков (см. [dashboard-jql-contract.md](file:///d:/Anti/specs/003-urgent-line-jira/contracts/dashboard-jql-contract.md)):
  1. Активные P1
  2. Активные P2
  3. Все открытые ургентные тикеты
  4. Просроченные инциденты
  5. Счетчики объема инцидентов
  6. Диаграмма инцидентов по типам
  7. Статистика по торговым точкам
  8. Метрики времени первой реакции
  9. Метрики времени итогового решения

### Этап 12: Проведение сквозного тестирования сценариев P1/P2
* Выполнить сквозное тестирование создания инцидента P1 и мгновенной эскалации.
* Проверить тайминги доставки уведомлений (лимит ≤ 60 сек).
* Провести тикет P2 через все статусы жизненного цикла с проверкой паузы SLA и валидатора резолюции.

### Этап 13: Проверка прав доступа и барьеров безопасности
* Провести аудит доступа с непривилегированной учетной записи (проект скрыт, поиск не выдает задачи).
* Проверить неизменяемость автора (`Reporter`) и корректность логирования всех действий в истории задач.

### Этап 14: Передача проекта в промышленную эксплуатацию
* Провести инструктаж сотрудников отдела жалоб и рабочей группы `Urgent Team`.
* Передать регламент работы с Kanban-доской и мониторинга Dashboard.
* Подписать протокол ввода проекта в промышленную эксплуатацию.
